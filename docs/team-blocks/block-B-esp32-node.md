# Блок B — ESP32-вузол (WiFi + MQTT)

> Перед цим прочитай `00-overview-shared-contract.md` — там топіки,
> IP-адреси, назви бібліотек.

## Твоя зона відповідальності

Прошивка для двох реальних ESP32: підключення до WiFi і MQTT-брокера,
публікація пакетів протоколу (з Блоку A), буферизація при розриві зв'язку.
Це саме та частина, де "фізичний прототип" стає реальним, а не імітацією.

## Рівень 1 — Bring-up: WiFi + MQTT, ще без протоколу

### Завдання
1. Встанови Arduino IDE (чи PlatformIO, якщо звичніше), плату ESP32
   (Board Manager → esp32), бібліотеку `PubSubClient` (Library Manager).
2. Прошивка-мінімум: підключення до WiFi (SSID/пароль вашої мережі),
   підключення до MQTT-брокера за LAN IP ноутбука Блоку C (домовтесь про
   цю адресу заздалегідь, вона зміниться, якщо ноутбук переключить мережу).
3. Раз на секунду публікуй у топік `case24/uplink` **простий текстовий
   рядок** (наприклад, `"hello from node 1"`, лічильник) — ще без
   структури пакета, це просто перевірка, що WiFi+MQTT працюють.
4. Перевір прийом: у терміналі на ноутбуці (з встановленим mosquitto)
   виконай:
   ```
   mosquitto_sub -h localhost -t case24/uplink
   ```
   Маєш бачити свої тестові рядки з ESP32 в реальному часі.

### Готово, коли
- `mosquitto_sub` показує повідомлення з реальної плати, кожну секунду,
  без розривів (окрім свідомого вимкнення WiFi).
- Те саме повторено на ДРУГІЙ платі (інший `node_id`, той самий брокер) —
  обидві бачаться одночасно в `mosquitto_sub`.

## Рівень 2 — Реальний протокол замість тестового рядка

### Завдання
1. Скопіюй `protocol.h`/`protocol.c` (Блок A) у папку скетча ESP32
   (Arduino компілює всі `.c`/`.h` файли в тій же папці, що й `.ino`).
2. Замість текстового рядка — зібрати справжній `SensorPacket`
   (`msg_type = MSG_HEARTBEAT` раз на 5с, `msg_type = MSG_TELEMETRY` раз
   на 2с із показниками — реальний датчик, якщо є, або `random()` в C,
   якщо датчика ще нема), викликати `protocol_pack()`, опублікувати
   результат байтами (не текстом!) у `case24/uplink`.
3. `sequence` — власний лічильник `uint32_t`, +1 з кожним відправленим
   пакетом (той самий підхід, що і в Python-версії).
4. Перевір разом із Блоком C: Gateway (коли буде готовий бодай на своєму
   Рівні 1) має правильно розпакувати саме твої реальні пакети.

### Готово, коли
- Gateway показує реальні дані з ESP32 (не тестові рядки) з правильним
  `node_id` і зростаючим `sequence`.

## Рівень 3 — Буфер і розрив зв'язку (найважливіший рівень для демо)

### Завдання
1. Заведи в прошивці невеликий буфер (масив фіксованого розміру,
   наприклад `SensorPacket buffer[20]`, і лічильник, скільки заповнено —
   в C на мікроконтролері зручніше фіксований масив, ніж динамічна
   структура, пам'яті обмежено).
2. Перед кожною спробою `publish()` перевіряй, чи MQTT-клієнт підключений
   (`client.connected()` у `PubSubClient`). Якщо ні — клади пакет у буфер
   замість відправки (і не забудь: якщо буфер переповнився, вирішіть
   з командою, що робити — переписувати найстаріший запис, чи ігнорувати
   нові; зафіксуй рішення коментарем у коді).
3. Коли з'єднання відновлюється (`reconnect()` спрацював) — перед тим, як
   продовжити звичайну роботу, спочатку відправ усе, що накопичилось у
   буфері, підряд.
4. **Тестуй по-справжньому:** вимкни WiFi на роутері (чи відсунь плату
   поза зоною покриття) на 30 секунд, потім відновіть. Це не імітація —
   справжній розрив, і це саме той критерій приймання №4, який на демо
   виглядатиме особливо переконливо, бо це реальне залізо.

### Готово, коли
- Реальний 30-секундний розрив WiFi → після відновлення весь накопичений
  буфер долітає до Gateway, нічого не втрачено (перевір по `sequence` —
  чи всі номери підряд, без пропусків, навіть ті, що були "під час розриву").

## Рівень 4 — Обидві плати одночасно

### Завдання
1. Пропиши на другій платі інший `node_id` (константа в коді, змінюється
   перед прошивкою кожної плати).
2. Запусти обидві одночасно, тривалий час (5+ хвилин) — переконайся, що
   немає плутанини даних між ними на стороні Gateway.

### Готово, коли
- 2 реальні плати + симульований вузол Блоку D = 3 вузли одночасно
  видно окремо в dashboard Gateway. Це критерій приймання №1.
