## Що маємо по залізу

2 реальні ESP32-плати + 1 симульований (програмний) вузол — разом 3, що
закриває критерій приймання №1 ("мінімум 3 вузли одночасно"). Симульований
вузол пише той самий протокол і теж публікує в MQTT — з точки зору шлюзу
він не відрізняється від справжньої плати.

## Чотири блоки (усі — інженерна робота, ніхто не "тільки документи")

| Блок | Назва | Відповідає за |
|---|---|---|

| **B** | ESP32-вузол | WiFi, MQTT bring-up, публікація пакетів, буфер при розриві, 2 реальні плати |

## Спільний контракт — НЕ змінювати без узгодження з усією командою

### Структура пакета (C, той самий формат полів, що і в v1, тепер struct)

```c
#pragma pack(push, 1)   // без padding -- байти йдуть підряд, без "дірок"
typedef struct {
    uint8_t  version;      // версія протоколу, зараз = 1
    uint8_t  msg_type;      // див. enum нижче
    uint16_t node_id;       // ідентифікатор вузла
    uint32_t sequence;      // порядковий номер (per-node, наскрізний)
    uint64_t timestamp_ms;  // мс, час відправника
    uint16_t payload_len;   // довжина payload
    uint8_t  payload[MAX_PAYLOAD_SIZE];  // дані (JSON-рядок), фактично використана частина = payload_len
    uint32_t crc32;         // CRC32 від (усе, що вище, до заповненої частини payload)
} SensorPacket;
#pragma pack(pop)
```

`MAX_PAYLOAD_SIZE` — домовляємось на 128 байт (телеметрія невелика: пара
чисел у JSON, наприклад `{"t":21.4,"h":45.2}"` — це десь 20 байт, запас
достатній, а фіксований буфер такого розміру не обтяжує пам'ять ESP32).

**Важливо для Блоку A:** оскільки протокол тепер лежить у payload MQTT-
повідомлення, а не йде "сирим" по UDP — можна НЕ переганяти багатобайтові
поля (`sequence`, `timestamp_ms`) у мережевий порядок байтів (`htonl`), якщо
і ESP32, і ноутбук — little-endian (це типово і для Xtensa/RISC-V ESP32, і
для звичайних x86/ARM ноутбуків). Це свідоме спрощення — задокументувати
як припущення й обмеження (не буде працювати "з коробки" на big-endian
залізі, якщо колись таке з'явиться в проєкті).

### Типи повідомлень (той самий enum, що і в v1)

```c
typedef enum {
    MSG_HEARTBEAT = 0,  // best-effort, без ACK
    MSG_TELEMETRY = 1,  // best-effort, без ACK
    MSG_ALARM     = 2,  // критичне, потребує ACK/retry
    MSG_CONFIG    = 3,  // критичне, потребує ACK/retry
    MSG_ACK       = 4,  // підтвердження критичного повідомлення
} MessageType;
```

### MQTT: брокер, топіки, підключення

- **Брокер:** Mosquitto (безкоштовний, легкий, локальний). Встановлення:
  `brew install mosquitto` (Mac) або `apt install mosquitto` (Linux).
  Запуск: `mosquitto -v` (у терміналі, лишити працювати).
- **Хто де:** брокер піднімається на ноутбуці Блоку C (Gateway). ESP32
  підключається по WiFi до цього ноутбука за його **LAN IP-адресою**
  (не `localhost` — це працює лише всередині одного пристрою; ESP32 — це
  окремий пристрій у тій самій WiFi-мережі). Знайти IP ноутбука:
  `ipconfig getifaddr en0` (Mac, WiFi-адаптер) або `hostname -I` (Linux).
  **Обидва пристрої мають бути в одній WiFi-мережі.**
- **Топіки** (домовленість, щоб усі публікували/підписувались однаково):
  - `case24/uplink` — усі вузли (реальні й симульований) публікують сюди
    свої пакети (payload = сирі байти `SensorPacket`, серіалізовані).
    Gateway підписується на це один раз і розрізняє вузли за `node_id`
    усередині самого пакета (payload), не за топіком.
  - `case24/downlink/<node_id>` — Gateway публікує сюди ACK для
    конкретного вузла (наприклад, `case24/downlink/1` для вузла з
    `node_id=1`). Кожен вузол підписується лише на свій власний downlink-топік.
    Веб (Блок E) публікує сюди ж і CONFIG/ALARM-команди керування (серво,
    симуляція втрат) — Gateway на цей топік НЕ підписаний, конфлікту нема.
  - `case24/gateway/state` (додано 30.09) — Gateway публікує сюди СВІЙ вже
    оброблений стан (JSON: per-node received/lost/duplicate/online/loss_rate
    + corrupted_count), раз на 2с. **Веб (Блок E) читає ЛИШЕ цей топік для
    свого дашборду, а НЕ `case24/uplink` напряму** — інакше вийшло б два
    незалежні шлюзи з можливо різною статистикою. Дивись `gateway/README.md`.
- **Бібліотеки:** ESP32 (Arduino) — `PubSubClient` (Nick O'Leary,
  встановлюється через Library Manager в Arduino IDE). PC/Gateway (C) —
  `libmosquitto` (той самий пакет, що і брокер, містить ще й C-бібліотеку
  клієнта: `brew install mosquitto` встановлює і бібліотеку, і заголовки).

### Важливе застереження (питання до ментора, додати в список)

MQTT-брокер сам має QoS-рівні (0/1/2), які можуть частково забезпечувати
надійну доставку "з коробки". **Це не звільняє від власної реалізації
sequence/CRC/ACK/дедуплікації всередині payload** — кейс оцінює саме ВАШ
протокол усередині повідомлень, а не налаштування чужого брокера. Тримайте
QoS=0 (без гарантій від брокера) для чистоти демонстрації, поки не
уточнено з ментором, чи можна покладатись на QoS брокера частково.

### Чому все ще потрібен "Transport-адаптер", навіть з MQTT

Кейс вимагає, щоб заміна транспорту не вимагала переписування логіки
протоколу. Тому навіть зараз, з MQTT: обгорни відправку/прийом в тонкі
функції (`transport_send(bytes, len)` / `transport_recv(buffer, maxlen)`),
що всередині викликають MQTT-бібліотеку. Якщо ментор скаже перейти на
UDP — міняється тільки вміст цих двох функцій, а `protocol.c`,
трекінг вузлів, dashboard і решта логіки лишаються без змін.

**Оновлено 30.09 (3) — реалізовано, не лише задокументовано.** Три
фізичні плати тепер працюють на ТРЬОХ РІЗНИХ транспортах одночасно:
UDP, TCP (сирий сокет, без MQTT-обгортки) і UART (пряма дротова лінія
через USB-TTL перехідник до Pi). `gateway.c` слухає всі чотири канали
(+ MQTT, для `sim_node`/сумісності) одночасно, кожен свій `poll_*()`
передає сирі байти в ОДИН спільний `handle_packet()` — `protocol_unpack`,
дедуп, лічильники, ACK не знають і не питають, яким дротом прийшли
байти. ACK на критичне повідомлення йде назад ТИМ САМИМ каналом
(`ReplyRoute`), а не завжди в MQTT. Дашборд і `case24/gateway/state`
тепер показують, яким транспортом прийшов останній пакет кожного вузла.
Деталі й порти — `gateway/README.md` і `node_esp32/README.md`.

## П'ять критеріїв приймання (мета всіх чотирьох блоків)

| # | Критерій | Умова |
|---|---|---|
| 1 | Декілька вузлів | ≥3 вузли одночасно (2 реальних ESP32 + 1 симульований), шлюз показує кожен окремо |
| 2 | Втрата пакетів | 20% packet loss → критичні повідомлення доставлені, або зафіксовано вичерпання retry |
| 3 | Дублювання | повторний пакет не створює дублікат бізнес-події |
| 4 | Розрив зв'язку | розрив WiFi на 30с (реальний, на залізі!) → вузол буферизує, після відновлення шле накопичене |
| 5 | Пошкоджений пакет | відхиляється й фіксується в журналі, шлюз не падає |

## Структура репозиторію (нова, під C)

```

node_esp32/       — Arduino-скетч ESP32-вузла (Блок B)
gateway/          — C-програма шлюзу, лінкується з libmosquitto (Блок C)
sim_node/         — симульований вузол (C, той самий protocol.c) (Блок D)
tests/            — юніт-тести на C (codec round-trip, corrupt packet) (Блок A/D)
docs/             — специфікація, README, threat model, звіт (спільно, фінальний день)
python-reference/ — v1, Python-прототип, лишається як довідник, не як deliverable
```

## Фінальний день — РАЗОМ, не окремий блок

Презентація й документи не належать одній людині. В останній день (чи
раніше, паралельно, коли є вільна хвилина) кожен пише СВОЮ частину:
- Блок A: таблиця полів пакета + короткий опис enum.
- Блок B: як виглядав bring-up на залізі, які проблеми були з WiFi/MQTT.
- Блок C: скріншот/приклад dashboard, опис підходу до gap/duplicate.
- Блок D: результати тестів (loss/duplicate/corrupt/розрив) — конкретні числа.

Хтось один (будь-хто, по черзі) зводить це в один README + короткий звіт
під кінець дня 3. Це 1-2 години, не повноцінний окремий фронт роботи.
