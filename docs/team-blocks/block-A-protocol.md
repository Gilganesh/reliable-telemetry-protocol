# Блок A — Протокол (C)

> Перед цим прочитай `00-overview-shared-contract.md` — там уже готова
> структура пакета і enum, які тут просто реалізуються в код.

## Твоя зона відповідальності

Один файл `protocol.h` + `protocol.c`, який буде **буквально скопійований
без змін** і в ESP32-прошивку (Блок B), і в Gateway (Блок C), і в
симульований вузол (Блок D). Тут немає "своєї" програми, яка запускається
— це бібліотека, якою користуються всі інші. Тому найважливіше — щоб вона
компілювалась і працювала однаково всюди (звичайний, портативний C, без
нічого специфічного для Arduino чи для Linux/Mac).

## Рівень 1 — Структура і CRC32

### Завдання
1. `protocol.h` — оголошення `SensorPacket` (struct з `00-overview`),
   `MessageType` (enum), константа `MAX_PAYLOAD_SIZE = 128`.
2. `protocol.c` — функція CRC32. Ось перевірена реалізація (я сам
   скомпілював і перевірив на тестовому векторі `crc32("123456789") ==
   0xCBF43926` — це стандартне контрольне значення для цього алгоритму,
   можеш звірити сам, якщо будеш змінювати):

   ```c
   uint32_t crc32(const uint8_t *data, size_t len) {
       uint32_t crc = 0xFFFFFFFFu;
       for (size_t i = 0; i < len; i++) {
           crc ^= data[i];
           for (int bit = 0; bit < 8; bit++) {
               if (crc & 1u) crc = (crc >> 1) ^ 0xEDB88320u;
               else crc = crc >> 1;
           }
       }
       return ~crc;
   }
   ```
3. Функції пакування/розпакування:
   ```c
   // Заповнює out->crc32 сам. Повертає розмір "корисної" частини
   // (заголовок + payload_len байт payload + crc), яку реально треба
   // відправити -- не sizeof(SensorPacket) повністю (там же зайвий,
   // невикористаний хвіст payload-буфера).
   size_t protocol_pack(SensorPacket *pkt, uint8_t *out_buf, size_t out_buf_size);

   // 0 = ок, -1 = дані закороткі, -2 = CRC не збігається,
   // -3 = payload_len не збігається з фактичним розміром,
   // -4 = невідомий msg_type
   int protocol_unpack(const uint8_t *raw, size_t raw_len, SensorPacket *out_pkt);
   ```
   Логіка `protocol_unpack` — та сама, що вже перевірена в Python-версії
   (`protocol/packet.py`, метод `from_bytes`): спочатку перевірити мінімальну
   довжину, потім порахувати CRC від усього, крім останніх 4 байт, і
   порівняти з тим, що записано в останніх 4 байтах.
4. Юніт-тест (`tests/test_protocol.c`, звичайний C-файл з `main()`, без
   фреймворків): round-trip (запакував-розпакував, значення збігаються),
   і псування одного байта (CRC має це зловити, `protocol_unpack` має
   повернути `-2`, а не "впасти" — сегфолт тут вважається провалом тесту).

### Готово, коли
- `tests/test_protocol.c` компілюється (`cc tests/test_protocol.c
  protocol/protocol.c -o test_protocol -Iprotocol`) і виводить "усі тести
  пройшли" (сам вирішуєш формат виводу, головне — видно pass/fail).
- Псування одного байта в середині пакета — `protocol_unpack` повертає
  помилку, не крашиться.
- Псування одного байта в самих 4 байтах CRC — теж повертає помилку
  (симетрична перевірка, як ми розбирали на Python-версії).

## Рівень 2 — Уточнення енкодингу під реальні дані

### Завдання
1. Визнач, як саме `payload` кодується для `TELEMETRY` (домовся з Блоком B,
   що саме читає ESP32 з датчика). Найпростіше — короткий JSON-рядок
   (`{"t":21.4,"h":45.2}`), покласти його байти прямо в `payload[]`, довжину
   рядка — в `payload_len`. Якщо на ESP32 немає зручної JSON-бібліотеки —
   можна зібрати рядок вручну через `snprintf()`.
2. Допоможи Блоку C розпарсити цей JSON на прийомній стороні (можна
   найпростішим ручним парсингом, без бібліотеки, якщо формат завжди
   один і той самий і простий — або запропонуй легку C JSON-бібліотеку,
   наприклад `cJSON`, якщо хочеться зробити це надійніше).
3. Перевір разом з Блоком B і C: пакет, зібраний на ESP32, і пакет,
   зібраний твоїм тестовим C-кодом на ноутбуці — дають однаковий
   результат `protocol_unpack()` на прийомній стороні (Gateway).

### Готово, коли
- Реальний пакет від ESP32 (Блок B) успішно розпаковується у Gateway
  (Блок C) — жодних розбіжностей у полях.

## Рівень 3 — Підтримка команди в разі змін

Специфікація — це живий документ команди. Якщо хтось (Блок B чи C)
натрапляє на ситуацію, яку поточний формат не покриває (наприклад,
забагато даних для 128 байт payload, чи треба ще одне поле) — саме ти
вирішуєш, чи змінювати спільний `protocol.h`, і одразу повідомляєш усіх,
бо це файл, який лежить у трьох різних місцях одночасно (скопійований).

### Готово, коли
- Наприкінці проєкту всі три копії `protocol.c`/`protocol.h` (у
  `node_esp32/`, `gateway/`, `sim_node/`) — побайтово ідентичні.
