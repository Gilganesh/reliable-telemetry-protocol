# Алгоритм ACK/retry — однаковий для ESP32 (Блок B) і sim_node (Блок D)

> Це НЕ частина `protocol.c` — це логіка застосунку, кожен пише її
> у себе. Але алгоритм має бути однаковий, інакше поведінка на демо
> буде різною для реального вузла і для симуляції.

## Коли застосовується

Тільки для `MSG_ALARM` і `MSG_CONFIG` (критичні типи). `MSG_HEARTBEAT` і
`MSG_TELEMETRY` — best-effort, ACK не чекаємо, просто шлемо і забуваємо.

## Константи (домовтесь про однакові значення)

```c
#define ACK_TIMEOUT_MS   2000   // скільки чекати ACK, перш ніж повторити
#define MAX_RETRIES      3      // скільки РАЗ повторити (не рахуючи першу спробу)
```

## Псевдокод (однаковий для ESP32 і sim_node)

```
function send_critical(pkt):            // pkt.msg_type == MSG_ALARM або MSG_CONFIG
    attempts = 0
    while attempts <= MAX_RETRIES:
        publish(pkt)                     // той самий tx_buf, той самий sequence -- НЕ новий!
        deadline = now_ms() + ACK_TIMEOUT_MS

        while now_ms() < deadline:
            if ack_received_for(pkt.sequence):   // прийшов MSG_ACK з тим самим sequence
                log("ALARM seq=%d доставлено, спроб=%d", pkt.sequence, attempts+1)
                return SUCCESS
            // тут же продовжує обробляти вхідні MQTT-повідомлення (client.loop())
            // -- НЕ можна просто "спати" весь ACK_TIMEOUT_MS, бо MQTT-бібліотека
            // повинна встигати отримати ACK, який саме зараз прийде

        attempts += 1
        log("ALARM seq=%d: ACK не прийшов, спроба %d з %d", pkt.sequence, attempts, MAX_RETRIES+1)

    log("ALARM seq=%d: RETRY ВИЧЕРПАНО, повідомлення НЕ доставлено", pkt.sequence)
    return RETRY_EXHAUSTED
```

## Три деталі, які легко зробити неправильно

1. **`sequence` не змінюється між повторними спробами.** Це той самий
   пакет (ті самі байти в `tx_buf`), просто відправлений ще раз. Якщо
   згенерувати новий `sequence` на кожну спробу — шлюз побачить це як
   3 різні тривоги замість 1 повторної спроби, і дедуплікація (Блок C)
   не спрацює.
2. **Очікування ACK не повинно блокувати весь `loop()`.** На ESP32
   особливо: якщо просто `delay(2000)` — `client.loop()` (яка обробляє
   вхідні MQTT-повідомлення, включно з ACK) під час цього не викликається,
   і ACK ти "проґавиш" технічно, навіть якщо він прийшов. Потрібен цикл,
   що одночасно і чекає, і викликає `client.loop()`.
3. **Лог "retry вичерпано" — обов'язковий, не опційний.** Це прямо
   критерій приймання №2 з кейсу: "система фіксує вичерпання допустимої
   кількості retry". Без цього логу на демо нічим показати, що ця
   поведінка взагалі існує.

## Як тестувати без реального MQTT/заліза (Блок D, до появи Gateway)

`ack_received_for(sequence)` можна на старті просто заглушити (завжди
`false`) — це автоматично демонструє сценарій "retry вичерпано" без
потреби піднімати щось на іншому кінці. Це і є перший тест, який Артем
може прогнати сам, без Gateway.
