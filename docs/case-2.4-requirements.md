# Кейс №2.4

## 1. Назва кейсу

Надійний телеметричний канал для розподілених сенсорних вузлів

## 2. Напрям

Communication Systems

## 3. Контекст та проблема

Розподілені автономні сенсорні вузли мають передавати телеметрію на локальний шлюз навіть за нестабільного цифрового каналу зв'язку.

У реальних системах можуть виникати втрати пакетів, затримки, повторна доставка, порушення порядку пакетів або тимчасовий розрив з'єднання. Тому протокол має не лише передавати дані, а й контролювати їхню цілісність, відстежувати стан вузлів та забезпечувати коректне відновлення після проблем із каналом.

У межах кейсу складні умови зв'язку моделюються **в лабораторному середовищі**. Завдання не передбачає роботу з реальними бойовими мережами, підбір радіочастот, потужностей або антен.

Основний акцент робиться на надійності протоколу, спостережуваності системи та відтворюваному тестуванні.

## 4. Завдання команди

Розробити програмно-апаратний або повністю симуляційний прототип протоколу телеметрії для обміну даними між автономними сенсорними вузлами та локальним шлюзом.

Система має моделювати роботу:

- 3–10 сенсорних вузлів;
- 1 локального шлюзу.

Команда має реалізувати:

- адресацію вузлів;
- формат пакетів телеметрії;
- команди конфігурації;
- контроль цілісності повідомлень;
- Heartbeat;
- sequence number;
- timestamp;
- CRC або MAC на рівні демонстрації;
- ACK/retry для критичних повідомлень;
- буферизацію даних;
- механізм store-and-forward;
- виявлення втрат і дублювання пакетів;
- вимірювання характеристик каналу;
- dashboard або журнал стану вузлів.

Архітектура має дозволяти замінювати транспортний рівень без необхідності переписувати основну логіку протоколу.

## 5. Функціональні вимоги

### Ідентифікація вузлів

Кожен сенсорний вузол має мати:

- унікальний `node_id`;
- інформацію про версію протоколу.

### Формат пакетів

Пакет має містити щонайменше:

- type;
- sequence;
- timestamp;
- payload length;
- payload;
- перевірку цілісності.

Формат протоколу має бути документований таблицею полів та діаграмою станів.

### Контроль доставки

Шлюз має визначати:

- пропущені пакети;
- дублікати;
- порушення порядку пакетів.

Для критичних повідомлень необхідно реалізувати:

- ACK;
- обмежену кількість повторних спроб;
- фіксацію ситуації, коли допустиму кількість retry вичерпано.

Повторна доставка пакета не повинна створювати дублікати бізнес-подій.

### Робота при втраті зв'язку

Під час короткого розриву зв'язку сенсорний вузол має буферизувати дані.

Після відновлення каналу накопичені дані мають передаватися на шлюз за принципом store-and-forward.

### Конфігурація

Бажано передбачити передачу конфігурації вузла як окремого типу повідомлення.

### Dashboard та спостережуваність

Dashboard або система журналювання має дозволяти контролювати:

- online/offline стан вузлів;
- loss rate;
- latency;
- backlog.

### Транспортний рівень

Рекомендована архітектура:

```
Sensor Node → Transport Adapter → Impairment Simulator → Gateway → Event Store / Dashboard
```

Транспортний адаптер має бути замінним.

Однакова логіка протоколу має мати можливість працювати поверх:

- UDP;
- TCP;
- UART;
- імітованого каналу.

## 6. Технічні обмеження та умови

### Реалізація вузлів

Для створення сенсорних вузлів можуть використовуватися:

- ESP32;
- STM32;
- Raspberry Pi;
- програмні емулятори.

Допускається повна емуляція вузлів у Docker або окремих процесах.

### Симуляція нестабільного каналу

Необхідно забезпечити керовану симуляцію:

- packet loss;
- jitter;
- delay;
- duplication.

Для цього може використовуватися:

- Linux tc/netem;
- власний impairment proxy;
- інший програмний інструмент із відтворюваними параметрами.

### Обробка помилок

Неправильний або пошкоджений пакет не повинен призводити до аварійного завершення роботи всього шлюзу.

Пошкоджений пакет має бути:

- відхилений;
- зафіксований у журналі.

Для роботи з часом рекомендується використовувати monotonic time та явно документувати прийняті припущення щодо синхронізації.

### Безпека

Усі мережеві тести виконуються лише в локальному ізольованому середовищі.

Секрети не повинні зберігатися у відкритому вигляді в репозиторії.

Для демонстрації автентифікації повідомлень допускається використання стандартної бібліотеки. Розробка власної криптографії не передбачається.

У межах кейсу не передбачається:

- робота з реальними бойовими мережами;
- підбір частот, потужностей або антен для польового використання;
- розробка засобів перешкоджання зв'язку;
- обхід регуляторних вимог;
- передавання секретної або персональної інформації.

## 7. Вхідні дані та доступні ресурси

Для реалізації можуть використовуватися:

- ESP32 або STM32;
- Raspberry Pi;
- програмні емулятори вузлів;
- Wi-Fi;
- USB;
- UART;
- локальна мережа;
- схема референсного payload;
- скрипт або інструмент для внесення втрат і затримок.

### Рекомендований програмний стек

Для реалізації вузлів та шлюзу:

- Python;
- Go;
- C++;
- embedded C/C++.

Як тестовий транспорт:

- UDP;
- TCP;
- UART.

MQTT допускається як порівняльний baseline.

Для симуляції каналу:

- Linux tc/netem;
- програмний impairment proxy.

Для спостережуваності:

- Prometheus/Grafana;
- простий web dashboard;
- структуровані логи.

Для формату повідомлень можуть використовуватися:

- CBOR;
- MessagePack;
- Protocol Buffers;
- компактний власний формат із чіткою специфікацією.

## 8. Очікуваний результат

Команда має представити працездатний прототип телеметричної системи, що включає:

1. специфікацію протоколу;
2. реалізацію сенсорного вузла;
3. реалізацію шлюзу;
4. симулятор або стенд із декількома вузлами;
5. інструмент для моделювання нестабільного каналу;
6. логи та/або dashboard;
7. звіт про тестування при різних профілях каналу;
8. threat model високого рівня;
9. репозиторій;
10. інструкцію запуску та відтворення результату;
11. перелік відомих обмежень і технічного боргу.

### Критерії приймання

| # | Критерій | Умова |
|---|---|---|
| 1 | Робота декількох вузлів | Щонайменше 3 вузли одночасно передають дані, а шлюз відображає їх окремо |
| 2 | Втрата пакетів | При 20% packet loss критичні повідомлення мають бути доставлені або система має зафіксувати вичерпання допустимої кількості retry |
| 3 | Дублювання пакетів | При повторному отриманні пакета відповідна бізнес-подія не повинна дублюватися |
| 4 | Розрив зв'язку | При розриві каналу тривалістю 30 секунд вузол має буферизувати дані та передати накопичений буфер після відновлення зв'язку |
| 5 | Пошкоджений пакет | Пошкоджений пакет має бути відхилений та зафіксований у журналі без аварійного завершення роботи шлюзу |

## 9. Сценарій фінальної демонстрації

Під час фінальної демонстрації команда може:

1. Представити архітектуру системи та специфікацію розробленого протоколу.
2. Запустити щонайменше 3 сенсорні вузли та продемонструвати передачу телеметрії на шлюз.
3. Показати окреме відображення кожного вузла в dashboard або журналі.
4. Увімкнути профіль нестабільного каналу з контрольованими втратами та затримками пакетів.
5. Продемонструвати роботу ACK/retry при 20% packet loss.
6. Продемонструвати коректну обробку дубльованих та пошкоджених пакетів.
7. Відключити один із вузлів на 30 секунд та показати його перехід у стан offline.
8. Відновити з'єднання та продемонструвати передачу накопиченого backlog за механізмом store-and-forward.
9. Показати в dashboard або журналі loss rate, latency, backlog та online/offline стан вузлів.
10. Представити результати тестування при різних профілях каналу та пояснити відомі обмеження рішення.

Сценарій фінальної демонстрації команда може попередньо обговорити та узгодити з ментором.
