# Кейс №2.4 — Надійний телеметричний канал для розподілених сенсорних вузлів

Довідковий документ для команди (4 людини), хакатон, дедлайн — 3 дні.

## 1. Суть завдання

Напрям: Communication Systems.

Розподілені автономні сенсорні вузли передають телеметрію на локальний шлюз через нестабільний цифровий канал (втрати пакетів, затримки, повторна доставка, порушення порядку, тимчасові розриви). Потрібно розробити протокол і прототип, які не просто передають дані, а контролюють цілісність, відстежують стан вузлів і коректно відновлюються після проблем із каналом.

Складні умови зв'язку моделюються **в лабораторному середовищі** — повністю програмна симуляція, без роботи з радіочастотами, антенами, потужностями чи реальними бойовими мережами. Дозволена повна емуляція вузлів (Docker, окремі процеси). Залізо (ESP32/STM32/Raspberry Pi) — не обов'язкове, це опція «якщо залишиться час».

Акцент оцінки: надійність протоколу, спостережуваність системи, відтворюваність тестування.

## 2. Що система має моделювати

- 3–10 сенсорних вузлів, 1 локальний шлюз.
- Реалізувати: адресацію вузлів, формат пакетів телеметрії, команди конфігурації, контроль цілісності повідомлень, heartbeat, sequence number, timestamp, CRC/MAC, ACK/retry для критичних повідомлень, буферизацію даних, store-and-forward, виявлення втрат і дублювання пакетів, вимірювання характеристик каналу, dashboard/журнал стану вузлів.
- Архітектура має дозволяти замінити транспортний рівень (UDP/TCP/UART/імітований канал) без переписування основної логіки протоколу.

## 3. Функціональні вимоги (розгорнуто)

**Ідентифікація вузлів**: унікальний `node_id`, інформація про версію протоколу.

**Формат пакета** — щонайменше: `type`, `sequence`, `timestamp`, `payload length`, `payload`, перевірка цілісності (CRC/MAC). Формат має бути документований таблицею полів і діаграмою станів.

**Контроль доставки** — шлюз визначає: пропущені пакети, дублікати, порушення порядку пакетів.

**Критичні повідомлення** — потрібні: ACK, обмежена кількість retry, фіксація ситуації «retry вичерпано». Повторна доставка не повинна створювати дублікати бізнес-подій (дедуплікація за node_id + sequence).

**Робота при втраті зв'язку** — під час розриву вузол буферизує дані; після відновлення каналу накопичене передається на шлюз за принципом store-and-forward.

**Конфігурація** — бажано передавати конфігурацію вузла як окремий тип повідомлення.

**Dashboard / спостережуваність** — має показувати: online/offline стан вузлів, loss rate, latency, backlog.

**Транспортний рівень** — рекомендована архітектура:

```
Sensor Node → Transport Adapter → Impairment Simulator → Gateway → Event Store / Dashboard
```

Transport Adapter — замінний. Однакова логіка протоколу має працювати над UDP, TCP, UART, імітованим каналом.

## 4. Технічні обмеження та умови

- Вузли: ESP32, STM32, Raspberry Pi або програмні емулятори. Повна емуляція в Docker/окремих процесах — дозволена.
- Симуляція нестабільного каналу: керована симуляція packet loss, jitter, delay, duplication. Інструменти: Linux `tc/netem`, власний impairment proxy, інший інструмент із відтворюваними параметрами.
- Обробка помилок: неправильний/пошкоджений пакет не повинен призводити до аварійного завершення роботи шлюзу; такий пакет має бути відхилений і зафіксований у журналі.
- Час: рекомендується monotonic time, явно документувати припущення щодо синхронізації.
- Безпека: усі мережеві тести — лише в локальному ізольованому середовищі; секрети не зберігати відкритим текстом у репозиторії; для автентифікації повідомлень допускається стандартна бібліотека (власну криптографію не писати).
- **Поза межами кейсу**: реальні бойові мережі, підбір частот/потужностей/антен для польового використання, розробка засобів перешкоджання зв'язку, обхід регуляторних вимог, передавання секретної або персональної інформації.

## 5. Вхідні дані та ресурси

- Апаратно: ESP32/STM32, Raspberry Pi, програмні емулятори, Wi-Fi, USB, UART, локальна мережа, схема референсного payload, скрипт/інструмент для внесення втрат і затримок.
- Софт-стек (рекомендований, не обов'язковий): Python / Go / C++ / embedded C/C++.
- Транспорт для тестів: UDP / TCP / UART. MQTT допускається як порівняльний baseline.
- Симуляція каналу: Linux tc/netem, програмний impairment proxy.
- Спостережуваність: Prometheus/Grafana, простий web dashboard, структуровані логи.
- Формат повідомлень: CBOR, MessagePack, Protocol Buffers, або компактний власний формат із чіткою специфікацією.

## 6. Очікуваний результат (deliverables)

1. Специфікацію протоколу
2. Реалізацію сенсорного вузла
3. Реалізацію шлюзу
4. Симулятор або стенд із декількома вузлами
5. Інструмент для моделювання нестабільного каналу
6. Логи та/або dashboard
7. Звіт про тестування при різних профілях каналу
8. Threat model високого рівня
9. Репозиторій
10. Інструкцію запуску та відтворення результату
11. Перелік відомих обмежень і технічного боргу

## 7. Критерії приймання (мають пройти на демо)

| # | Критерій | Умова |
|---|---|---|
| 1 | Робота декількох вузлів | Щонайменше 3 вузли одночасно передають дані, шлюз відображає їх окремо |
| 2 | Втрата пакетів | При 20% packet loss критичні повідомлення доставлені, або система фіксує вичерпання допустимої кількості retry |
| 3 | Дублювання пакетів | Повторне отримання пакета не створює дублікат бізнес-події |
| 4 | Розрив зв'язку | При розриві на 30 секунд вузол буферизує дані і передає накопичений буфер після відновлення зв'язку |
| 5 | Пошкоджений пакет | Відхиляється і фіксується в журналі, без аварійного завершення роботи шлюзу |

## 8. Сценарій фінальної демонстрації (10 кроків із ТЗ)

1. Представити архітектуру системи та специфікацію протоколу.
2. Запустити щонайменше 3 сенсорні вузли, продемонструвати передачу телеметрії на шлюз.
3. Показати окреме відображення кожного вузла в dashboard/журналі.
4. Увімкнути профіль нестабільного каналу з контрольованими втратами й затримками.
5. Продемонструвати роботу ACK/retry при 20% packet loss.
6. Продемонструвати коректну обробку дубльованих і пошкоджених пакетів.
7. Відключити один із вузлів на 30 секунд, показати перехід у стан offline.
8. Відновити з'єднання, продемонструвати передачу backlog (store-and-forward).
9. Показати в dashboard/журналі loss rate, latency, backlog, online/offline стан вузлів.
10. Представити результати тестування при різних профілях каналу, пояснити відомі обмеження.

Сценарій можна попередньо погодити з ментором.

## 9. Рішення команди

Дивись `docs/team-blocks/00-overview-shared-contract.md` — там актуальна (v2) версія рішень: усе на C, ESP32 + MQTT, 2 реальні плати + 1 симуляція.

Питання, які чекають підтвердження від ментора: точне визначення «критичного повідомлення», ліміт retry й timeout, розмір буфера і поведінка при переповненні, чи обов'язкова заміна транспорту на демо, чи достатньо CRC32 чи очікується HMAC, критерії оцінки (демо vs звіт vs специфікація), чи достатньо MQTT QoS чи потрібен власний ACK понад ним.
