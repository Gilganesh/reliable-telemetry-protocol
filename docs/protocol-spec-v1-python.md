# Специфікація протоколу телеметрії (v1, чернетка Дня 1)

> Статус: базовий формат зафіксований і реалізований. Розділи "критичні
> повідомлення" та "стан вузла" будуть доповнені на День 2 (ACK/retry,
> буферизація, store-and-forward). Це чернетка для фінального звіту, не
> остаточний документ.

## 1. Формат пакета

Мережевий порядок байтів (big-endian, `!` у Python `struct`).

| Поле       | Розмір  | Тип (struct) | Опис                                          |
|------------|---------|---------------|-----------------------------------------------|
| version    | 1 байт  | `B`           | Версія протоколу (поточна = 1)                |
| msg_type   | 1 байт  | `B`           | Тип повідомлення, див. таблицю нижче          |
| node_id    | 2 байти | `H`           | Ідентифікатор вузла (0–65535)                 |
| sequence   | 4 байти | `I`           | Порядковий номер пакета (per-node, глобальний across типів) |
| timestamp  | 8 байт  | `Q`           | Час відправлення, мс, wall-clock відправника  |
| pay_len    | 2 байти | `H`           | Довжина payload у байтах                      |
| payload    | 0..1000 байт | —        | Корисні дані (JSON для telemetry/alarm/config)|
| crc32      | 4 байти | `I`           | CRC32 від (усіх попередніх полів разом)       |

Заголовок = 18 байт, повний overhead (заголовок + crc) = 22 байти.
Максимальний розмір payload — 1000 байт (щоб уникнути фрагментації в
типовій Ethernet-мережі з MTU 1500).

```
 0        1        2                 4                              12       14                   14+N   14+N+4
 +--------+--------+-----------------+------------------------------+--------+---------------------+--------+
 |version | msg_type|      node_id   |          sequence            |      ...timestamp (8B)...     |pay_len |
 +--------+--------+-----------------+------------------------------+--------+---------------------+--------+
 |                                   payload (N байт)                                                | crc32  |
 +----------------------------------------------------------------------------------------------------+--------+
```
(Спрощена схема; точні зсуви — у `protocol/packet.py`, це джерело правди.)

## 2. Типи повідомлень

| Значення | Назва      | ACK потрібен? | Хто відправляє      | Призначення                          |
|----------|------------|---------------|----------------------|---------------------------------------|
| 0        | HEARTBEAT  | Ні (best-effort) | Node → Gateway    | "я живий", ознака online/offline      |
| 1        | TELEMETRY  | Ні (best-effort) | Node → Gateway    | дані сенсорів (JSON payload)          |
| 2        | ALARM      | **Так**       | Node → Gateway       | критична подія (поріг перевищено)     |
| 3        | CONFIG     | **Так**       | Gateway → Node       | команда конфігурації вузла             |
| 4        | ACK        | —             | приймач → відправник | підтвердження критичного повідомлення |

**Рішення команди (п.9 project-context.md, очікує підтвердження ментора):**
критичні = ALARM + CONFIG. Телеметрія й heartbeat — best-effort, без ACK/retry.

## 3. Ідентифікація та цілісність

- `node_id` — унікальний для кожного вузла, призначається вручну при старті (CLI-аргумент).
- Цілісність — CRC32 (не MAC/HMAC). Причина: демо-рівень, стандартна бібліотека
  `zlib.crc32`, без власної криптографії (відповідає п.4 ТЗ "Безпека").
  HMAC для CONFIG/ALARM — можливе доповнення Дня 2, якщо ментор підтвердить
  вимогу автентифікації команд (а не лише цілісності).

## 4. Час

- `timestamp` у пакеті — wall-clock (`time.time()*1000`) відправника,
  бо це поле передається між процесами і `monotonic()` одного процесу
  не має сенсу для іншого.
- Для локальних інтервалів (heartbeat, telemetry, майбутні retry-таймаути,
  online/offline на gateway) — `time.monotonic()`.
- Синхронізація годинників між вузлом і gateway не гарантується
  (демо в одній локальній мережі/машині, NTP-дрейф ігнорується).

## 5. Sequence, gap, duplicate (реалізовано, День 1)

- `sequence` — один зростаючий лічильник на вузол, спільний для всіх типів
  повідомлень цього вузла (простіше для gap-аналізу на gateway).
- Gateway тримає `max_seq_seen` на кожен `node_id`:
  - `seq > max_seq_seen` → новий пакет (можливий gap, якщо `seq - max_seq_seen - 1 > 0`)
  - `seq <= max_seq_seen` → трактується як duplicate/out-of-order (Day 1: без розрізнення)

**Відомий технічний борг Дня 1** (задокументовано свідомо, не помилка):
точна дедуплікація *бізнес-подій* за `(node_id, sequence)` — тобто
розрізнення "це реальний дублікат" від "пакет прийшов пізніше, ніж мав" —
буде додана на День 2 разом з ACK/retry-логікою.

## 6. Стан вузла на gateway (реалізовано, День 1)

`online` / `offline` визначається за `now - last_seen > offline_timeout`
(конфігурований, за замовчуванням 15с; для критерію приймання #4 "розрив
на 30с" використовуємо коротший таймаут, напр. 5–8с, щоб офлайн-перехід
було видно раніше за 30-секундний розрив — уточнити на Дні 2 разом з
impairment proxy).
